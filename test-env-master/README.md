# QA Workbench

QA Workbench یک میزکار محلی برای مهندسی تست است. نیازمندی را از Jira یا فایل صفحه‌گسترده دریافت می‌کند، با هوش مصنوعی تحلیل و Test Case تولید می‌کند، اجرای تست و Bug را ثبت می‌کند و پیش‌شرط‌های تست را — با مراحل UI در مرورگر، درخواست‌های API و عملیات Database — روی محیط تست آماده می‌کند.

همه‌چیز روی ماشین خودتان باقی می‌ماند. Jira اختیاری است و بدون آن سیستم با داده نمایشی یا فایل Excel/CSV کار می‌کند. تحلیل Test Workspace به یک سرویس هوش مصنوعی (محلی یا آنلاین) نیاز دارد؛ بقیهٔ بخش‌ها بدون آن هم کار می‌کنند.

رابط کاربری تیره، فشرده و دوزبانه است. فارسی به‌صورت RTL و انگلیسی به‌صورت LTR نمایش داده می‌شود. اعداد و تاریخ نیز در حالت فارسی با ارقام و تقویم فارسی نمایش داده می‌شوند.

## قابلیت‌ها

### ورود نیازمندی

Issue را می‌توان مستقیماً از Jira دریافت کرد یا از فایل Excel و CSV وارد کرد.

یک Issue نمایشی نیز وجود دارد تا بدون اتصال به Jira بتوان کل Flow سیستم را مشاهده و تست کرد.

توکن Jira به‌صورت رمزنگاری‌شده ذخیره می‌شود و پس از ذخیره مجدداً به Client برگردانده نمی‌شود.

### تحلیل و طراحی تست

تحلیل Test Workspace با مدل زبانی انجام می‌شود و برای هر Requirement این خروجی‌ها را می‌سازد:

- خلاصه و فهم ساختاریافتهٔ نیازمندی: قواعد کسب‌وکار (R1، R2، …)، APIها، وضعیت‌ها و گذارها، پیکربندی و فرمول‌ها، جریان‌ها و مدل داده
- معیارهای پذیرش (اگر تسک AC نداشته باشد، از روی توضیحات و PRD پیشنهاد می‌شوند)
- شکاف‌ها، ابهام‌ها و پرسش‌ها از محصول، توسعه‌دهنده و کسب‌وکار
- Test Strategy، Test Cases، Edge Cases، Risks و پیشنهاد Automation

#### تحلیل چندمرحله‌ای

تحلیل در پس‌زمینه و در چند مرحله اجرا می‌شود و پیشرفت هر مرحله و مدلی که روی آن کار می‌کند در صفحه دیده می‌شود:

1. خلاصه‌سازی اسناد طولانی (فقط اگر در Context مدل جا نشوند)
2. فهم نیازمندی
3. معیارهای پذیرش
4. شکاف‌ها، پرسش‌ها، ریسک‌ها و استراتژی، و هم‌زمان با آن طراحی Test Case، حالات مرزی و ترجمه
5. بازبینی مستقل توسط یک مدل دیگر
6. پیشنهاد Automation

برای جلوگیری از خروجی ساختگی:

- هر قاعده و هر معیار پیشنهادی باید جمله‌ای از متن خود تسک یا PRD را به‌عنوان شاهد بیاورد؛ شاهدی که در متن پیدا نشود اطمینان را «نامطمئن» می‌کند.
- مرحلهٔ بازبینی موارد بی‌پشتوانه، تکراری یا مبهم را حذف یا اصلاح می‌کند.
- معیارهای پیشنهادی هوش مصنوعی تا وقتی تأیید نشوند «پیشنهاد» هستند و Test Caseهای آن‌ها «نیازمند بازبینی» علامت می‌خورند.

#### زبان تحلیل

با دو دکمهٔ «تحلیل فارسی» و «تحلیل انگلیسی»، همهٔ خروجی‌ها به زبان انتخاب‌شده نوشته می‌شوند، به هر زبانی که تسک نوشته شده باشد. اگر زبان تسک با زبان تحلیل فرق کند، ترجمهٔ آن هم برای نمایش ساخته می‌شود و متن اصلی Jira هیچ‌وقت تغییر نمی‌کند.

#### PRD

برای هر تسک می‌توان به‌صورت اختیاری PRD یا اسناد کسب‌وکاری اضافه کرد: متن را Paste کنید یا فایل ‎.md، ‎.txt، ‎.pdf یا ‎.docx بارگذاری کنید. تحلیل این اسناد را همراه تسک می‌خواند تا منطق کسب‌وکاری که فقط در PRD آمده هم تحلیل و تست شود.

#### ویرایش و یادگیری

همهٔ خروجی‌ها قابل ویرایش هستند: خلاصه، شکاف‌ها، پرسش‌ها، معیارها، Test Caseها، حالات مرزی، ریسک‌ها، استراتژی و Automation.

- هر اصلاح (ویرایش، حذف، تأیید یا رد پیشنهاد) ثبت می‌شود.
- آخرین اصلاحات هر نوع خروجی دفعهٔ بعد به‌عنوان نمونه به مدل داده می‌شود.
- اصلاحات به‌صورت دوره‌ای به «رهنمود» تبدیل می‌شوند.
- رهنمودها در «تنظیمات ← آنچه تحلیل یاد گرفته» دیده، ویرایش، خاموش یا حذف می‌شوند و می‌توان قواعد دلخواه هم نوشت.

مواردی که کاربر ویرایش یا تأیید کرده در اجراهای بعدی دست نمی‌خورند. Test Caseهای تولیدشده‌ای که دیگر تولید نشوند حذف می‌شوند، مگر اجرا شده باشند که در این صورت «احتمالاً قدیمی» علامت می‌خورند.

#### سرویس‌های هوش مصنوعی

در «تنظیمات ← AI provider» می‌توان چند سرویس اضافه کرد. هر مرحلهٔ تحلیل از سرویس خودش استفاده می‌کند؛ اگر یک سرویس در دسترس نباشد یا محدودیت نرخ بدهد، سرویس بعدی امتحان می‌شود و بازبینی تا جای ممکن با مدلی غیر از مدل نویسندهٔ Test Caseها انجام می‌شود.

| سرویس | توضیح |
|---|---|
| Ollama یا LM Studio | محلی، رایگان و خصوصی. مدل از همان صفحه دانلود می‌شود. |
| Pollinations | رایگان، بدون حساب و کلید؛ از ایران بدون VPN در دسترس است. |
| Hugging Face، GitHub Models، SambaNova، Mistral | پلن رایگان با کلید؛ از ایران بدون VPN در دسترس‌اند. |
| Cerebras | پلن رایگان با کلید؛ ممکن است VPN لازم باشد. |
| Groq، Google Gemini، OpenRouter | پلن رایگان؛ ممکن است VPN لازم باشد. |

برای سرویس‌های بیرون از شبکه باید اجازهٔ ارسال متن نیازمندی صریحاً داده شود. کلید API رمزنگاری‌شده ذخیره می‌شود و اطلاعات محرمانهٔ داخل متن تسک پیش از ارسال پوشانده می‌شود.

هر تحلیل حداکثر ۳ دقیقه طول می‌کشد (قابل تنظیم). در پایان زمان، مراحل تمام‌شده ذخیره می‌شوند. جزئیات در بخش [راه‌اندازی هوش مصنوعی](#راه‌اندازی-هوش-مصنوعی) آمده است.

### مدیریت اجرای تست

Test Caseها را می‌توان در Suiteهای مختلف مانند Smoke، Regression یا Suiteهای سفارشی قرار داد.

نتیجه اجرای Test Case ثبت می‌شود و از اجرای Failed می‌توان Bug ایجاد کرد.

Dashboard اطلاعاتی مانند موارد زیر را نمایش می‌دهد:

- Pass Rate
- Test Coverage
- Status Distribution
- Execution History

### پیش‌شرط‌ها (Preconditions)

بخش «پیش‌شرط‌ها» (قبلاً «سناریوها») برای آماده کردن شرایط لازم پیش از تست است: ساختن داده، ورود کاربر، رساندن سیستم به وضعیت موردنظر. هر پیش‌شرط مجموعه‌ای از Stepهای قابل اجراست. مسیر صفحه (`/scenarios`) و API تغییری نکرده‌اند.

Stepها می‌توانند شامل موارد زیر باشند:

- مرحلهٔ UI (مرورگر): ضبط کارها در مرورگر و تکرار خودکار آن‌ها در پس‌زمینه
- HTTP Request
- Assertion
- Variable Extraction
- Set Variable
- Delay
- Condition
- Database Operation

صفحهٔ پیش‌شرط سه بخش اصلی دارد:

- **Overview:** نام، توضیح، Environment، دکمه‌های Run / Stop / Run again، Progress و خلاصه Stepهای موفق، ناموفق، ردشده و در انتظار.
- **Request Flow:** فهرست فشرده Stepها با Method، URL، وضعیت، Status Code، مدت اجرا و نشانگر اینکه Step از داده کدام Stepهای قبلی استفاده می‌کند.
- **Step Panel:** با انتخاب هر Step باز می‌شود و Tabهای Request، Response، Data Mapping، Assertions، Attempts و Advanced دارد.

#### مرحلهٔ UI (ضبط در مرورگر)

مرحلهٔ UI کاری را که کاربر در یک وب‌سایت انجام می‌دهد یاد می‌گیرد و بعداً همان را در پس‌زمینه انجام می‌دهد. مثل بقیهٔ Stepها رفتار می‌کند: در Flow جابه‌جا، خاموش، تکثیر و «اجرا تا همین مرحله» می‌شود و کنار Stepهای HTTP و دیتابیس قرار می‌گیرد.

**ضبط:**

1. «افزودن ← مرحلهٔ UI (مرورگر)» را بزنید و آدرس شروع را وارد کنید.
2. «شروع ضبط» یک پنجرهٔ Chrome روی همین کامپیوتر باز می‌کند. کار موردنظر را انجام دهید: کلیک روی دکمه‌ها و لینک‌ها، تایپ در فیلدها، انتخاب از فهرست، تیک زدن، Enter، رفتن به صفحهٔ دیگر یا باز شدن تب جدید.
3. هر اقدام همان لحظه در پنجرهٔ ضبط برنامه نمایش داده می‌شود. برای بررسی یک متن، آن را در صفحه انتخاب کنید و در نوار ضبطِ داخل صفحه «✓ check text» را بزنید.
4. با «توقف ضبط» (یا دکمهٔ stop نوار داخل صفحه، یا بستن پنجره) ضبط تمام می‌شود و با «ذخیرهٔ مرحله» Step ساخته می‌شود.

**یادگیری و اجرای درست:**

- هر عنصر به چند روش به خاطر سپرده می‌شود: `data-testid`، `id` پایدار، Role و نام قابل‌دسترس، Label، Placeholder، `name`، متن و CSS، به‌همراه اثرانگشت عنصر (برچسب، متن، کلاس‌ها).
- هنگام اجرا اول روشی امتحان می‌شود که دفعهٔ قبل جواب داده، بعد بقیهٔ روش‌ها، و اگر هیچ‌کدام نشد، شبیه‌ترین عنصر صفحه به اثرانگشت. اگر عنصر از راه دیگری پیدا شود (مثلاً صفحه بازطراحی شده)، راه جدید روی Step ذخیره می‌شود و اجرای بعد از همان شروع می‌کند.
- برای هر عنصر صبر می‌کند تا ظاهر و قابل کلیک شود، بعد از هر اقدام منتظر بارگذاری صفحه و درخواست‌های شبکه می‌ماند، و برای فیلدهای خاص که `fill` را قبول نمی‌کنند مثل کاربر تایپ می‌کند.
- تایپ‌های پشت‌سرهم یک فیلد یک اقدام می‌شوند و کلیکی که فقط فیلد را فعال کرده حذف می‌شود.
- رمز عبور، OTP و کدهای مشابه رمزنگاری‌شده ذخیره می‌شوند و دوباره به مرورگر فرستاده نمی‌شوند.

**نتیجه:**

- Tab «نتیجه» برای هر اقدام وضعیت، زمان، روش پیدا کردن عنصر و نشان «یاد گرفت» را نشان می‌دهد، همراه با آدرس صفحهٔ پایانی و تصویر صفحه.
- اگر بعد از آخرین کلیک یا Enter پیام خطایی در صفحه ظاهر شود (مثلاً «رمز اشتباه است»)، Step با همان پیام ناموفق می‌شود؛ این رفتار در گزینه‌های Step قابل خاموش کردن است.
- اگر عنصری پیدا نشود، Step می‌گوید کدام اقدام و چرا؛ اقدام‌های بعدی «اجرا نشد» علامت می‌خورند. اقدامی که «اختیاری» علامت خورده (مثلاً بستن بنر Cookie) اگر انجام نشود Step را ناموفق نمی‌کند.

**ویرایش:** در Tab «اقدام‌ها» توضیح و مقدار هر اقدام قابل تغییر است، اقدام‌ها جابه‌جا یا حذف می‌شوند، و «بررسی متن»، «بررسی آدرس»، «انتظار برای متن» و «باز کردن آدرس» اضافه می‌شوند. مقدارها می‌توانند `{{variable}}` داشته باشند. «ضبط بیشتر» اقدام‌های تازه را به انتها اضافه یا جایگزین اقدام‌ها می‌کند.

**اتصال به Stepهای بعدی:** بعد از اجرا، Cookieها، localStorage، sessionStorage و آدرس صفحه مقدارهایی هستند که Stepهای بعدی می‌توانند Map کنند؛ مثلاً Token ورودِ UI در `response.body.localStorage.auth.token` برای Header `Authorization` یک درخواست API. Stepهای UI پشت‌سرهم یک نشست مرورگر مشترک دارند (مگر «شروع در مرورگر جدید» روشن باشد) و مرورگر در پایان اجرا بسته می‌شود.

**پیش‌نیاز:** Google Chrome، Chromium یا Edge روی سیستمی که API روی آن اجرا می‌شود (مسیر دیگر با `UI_BROWSER_PATH`). ضبط به صفحه‌نمایش همان سیستم نیاز دارد و اجرا بدون پنجره (Headless) انجام می‌شود. Image پیش‌فرض Docker مرورگر ندارد؛ برای مراحل UI، API را بدون Docker اجرا کنید یا Chrome را به Image اضافه و `UI_BROWSER_PATH` را تنظیم کنید.

**رفع مشکل مرحلهٔ UI:**

| مشکل | علت و راه‌حل |
|---|---|
| «No Chrome, Chromium or Edge was found» | مرورگر نصب نیست یا در مسیر شناخته‌شده نیست؛ Google Chrome را نصب کنید یا مسیرش را در `.env` با `UI_BROWSER_PATH` بدهید و API را دوباره اجرا کنید. |
| پنجرهٔ ضبط باز نمی‌شود | API باید روی همان کامپیوتری اجرا شود که صفحه‌نمایش دارد (در لینوکس از Terminal داخل محیط گرافیکی، تا `DISPLAY` تنظیم باشد). |
| «Element not found» | صفحه آن‌قدر تغییر کرده که عنصر حتی با شباهت هم پیدا نشده؛ آن اقدام را حذف و با «ضبط بیشتر» دوباره ضبط کنید، یا «انتظار برای هر عنصر» را در گزینه‌ها بیشتر کنید. |
| «The page shows an error: …» | صفحه بعد از آخرین اقدام پیام خطا نشان داده (مثلاً رمز اشتباه)؛ مقدارها را بررسی کنید. اگر این پیام همیشگی است، گزینهٔ مربوطش را خاموش کنید. |
| «The secret value of this action is missing» | رمز این اقدام با کلید دیگری رمزنگاری شده یا پاک شده است (مثلاً `SECRETS_ENCRYPTION_KEY` عوض شده)؛ آن را در Tab «اقدام‌ها» دوباره تایپ کنید. |
| ضبط بعد از ۳۰ دقیقه بسته شد | ضبطی که ۳۰ دقیقه اقدامی نداشته باشد خودکار بسته می‌شود؛ اقدام‌های ضبط‌شده تا آن لحظه حفظ می‌شوند. |

#### ورود چند cURL

در دیالوگ «Import cURL» می‌توان چند دستور cURL را (جدا شده با خط خالی) یکجا Paste کرد.

قبل از ذخیره، یک صفحه Review نمایش داده می‌شود که شامل موارد زیر است:

- Method، URL، تعداد Headerها و نوع Body هر Request
- Warningها مثل Header تکراری، Optionهای پشتیبانی‌نشده یا اعمال‌نشده (`-k`، `-L`، `--proxy`) و Request تکراری
- دستورهای Malformed همراه با علت خطا (این دستورها Import نمی‌شوند)
- ارتباط‌های شناسایی‌شده بین Requestها که با Checkbox انتخاب می‌شوند

دستور cURL اصلی در Config هر Step نگه داشته می‌شود. Import هیچ Requestی را اجرا نمی‌کند.

#### شناسایی خودکار وابستگی‌ها

سیستم بررسی می‌کند کدام فیلد یک Request احتمالاً از پاسخ یک Request قبلی می‌آید؛ مثلاً Token در Header `Authorization` یا شناسه کاربر در URL Path. شواهد به ترتیب قدرت:

1. فیلدهایی که Retry خودکار در آخرین اجرا آن‌ها را درست کرده است
2. مقدارهایی که عیناً در یک Response واقعی دیده شده‌اند
3. استنباط فقط از روی Requestها (مثلاً Token صادرشده توسط Login، یا Requestی که یک Entity را می‌سازد یا برمی‌گرداند)؛ این موارد با برچسب «Inferred» نشان داده می‌شوند و هیچ‌وقت High Confidence نیستند

پیشنهادها تا وقتی کاربر آن‌ها را Accept نکند یا دکمهٔ «تشخیص خودکار Mappingها» را نزند اعمال نمی‌شوند. فیلدی که Mapping ذخیره‌شده دارد پیشنهاد جدید نمی‌گیرد.

#### تشخیص خودکار Mappingها

دکمهٔ «تشخیص خودکار Mappingها» بالای Request Flow (برای کل پیش‌شرط) و در Tab «Data Mapping» (برای همان Step) است. مثلاً بعد از پاک کردن Mappingها:

- برای هر فیلدی که Mapping ندارد، با همان سه نوع شواهد بالا پیدا می‌کند مقدارش از پاسخ کدام Step قبلی می‌آید.
- از آخرین پاسخ موفق هر Step در اجراهای اخیر استفاده می‌کند؛ اگر آخرین اجرا وسط کار متوقف شده باشد، پاسخ‌های اجراهای قبلی هم به کار می‌آیند. پاسخ‌های ناموفق یا دارای خطا شاهد حساب نمی‌شوند.
- فقط موارد روشن ذخیره می‌شوند. فیلدی که دو منبع هم‌ارز دارد یا فقط شواهد ضعیف (Low) دارد ذخیره نمی‌شود و به‌صورت پیشنهاد می‌ماند، چون Mapping اشتباه از نداشتن Mapping بدتر است.
- Mappingهای استنباط‌شده از روی Requestها در اجرای بعدی با پاسخ واقعی تأیید می‌شوند. اگر پیش‌شرط هنوز اجرا نشده باشد، پیام می‌دهد یک بار اجرا کنید.

#### Data Mapping بدون Variable

کاربر برای اتصال Requestها نیازی به تعریف Variable یا نوشتن JSONPath ندارد:

- در Tab «Request» کنار هر فیلد (Path، Query، Header، JSON Body، Form) گزینه «پر کردن از پاسخ قبلی» وجود دارد.
- در Tab «Response» با Response Explorer (درختی، قابل جستجو، با نمای Raw) می‌توان یک مقدار را انتخاب و «در درخواست بعدی استفاده» کرد.

Mapping روی خود Step ذخیره می‌شود (`config.bindings`) و فقط **محل** مقدار ذخیره می‌شود، نه خود مقدار. در هر اجرا مقدار دوباره از پاسخ همان اجرا خوانده می‌شود. Mappingهای Inferred بعد از اولین اجرای موفق به Path واقعی Pin و Verified می‌شوند.

Tab «Data Mapping» وضعیت هر Mapping را نشان می‌دهد و Mappingهایی را که نیاز به بررسی دارند علامت می‌زند: Step مبدأ حذف شده، بعد از مقصد اجرا می‌شود یا خاموش است، فیلد مقصد دیگر وجود ندارد، یا مقدار در آخرین Response نیست. Mappingها قابل تغییر، خاموش/روشن و حذف هستند. Mapping انتخابی کاربر بر Mapping شناسایی‌شده اولویت دارد و مبدأ همیشه باید یک Step قبلی از همان پیش‌شرط باشد.

#### شرط موفقیت و تحلیل پاسخ

- شرط موفقیت از `expectedStatus` و Assertionهای بعد از Step خوانده می‌شود؛ در نبود آن‌ها هر Status 2xx یا 3xx موفق است و 4xx و 5xx ناموفق.
- Redirectها دنبال نمی‌شوند، ولی Response با Status 3xx یک پاسخ عادی است: پیش‌شرط متوقف نمی‌شود و هدر `Location` و Cookieهای آن (مثلاً Session بعد از Login) در Stepهای بعدی قابل استفاده‌اند.
- بدنهٔ پاسخ هم بررسی می‌شود: اگر پاسخ حتی با 2xx خطا گزارش کند، Step ناموفق است و پیش‌شرط ادامه نمی‌دهد. نمونه‌ها: `success: false`، `ok: false`، `status: "error"`، فهرست پر `errors`، شیء `error`، یا `errorCode` غیرصفر.
- فقط علامت‌های سطح اول پاسخ حساب می‌شوند؛ Entityای که خودش `status: "FAILED"` دارد، `errors: []` یا `code: 0` خطا نیستند.
- اگر Assertionی خودش این فیلدها را بررسی کند (Test منفی، مثلاً `body.success = false`)، همان Assertion تصمیم می‌گیرد. در Tab «Assertions» هم می‌توان این بررسی را برای هر Step خاموش کرد.

خطای پاسخ به فیلد Request و Mapping مربوطش وصل می‌شود:

- فیلدی که پاسخ صریحاً نام می‌برد (`field`، `param`، `errors[0].field`، یا کلیدهای `errors: { orderId: [...] }`)
- فیلدی که پیام خطا به آن اشاره می‌کند («order item id is invalid» ← `orderItemId`)
- Header یا Cookie احراز هویت برای خطاهای Token و Session

کارت خطا در Tabهای Response و Data Mapping پیام، محل تشخیص و کد خطا را نشان می‌دهد، می‌گوید آن فیلد از کدام Step و مسیر پر می‌شود (یا Mapping ندارد) و دکمهٔ تغییر یا ساخت Mapping دارد. Retry خودکار هم اول اصلاح همان فیلد را امتحان می‌کند.

#### اجرا، Retry و Recovery

- اجرای پیش‌شرط به‌صورت Live انجام می‌شود و قابل Cancel است. «اجرا تا همین مرحله» یک Step را همراه با Stepهای قبلی‌اش در یک Context تازه اجرا می‌کند.
- اگر مقدار یک Mapping در اجرای جاری موجود نباشد، Step با وضعیت **Blocked** متوقف می‌شود و Request با مقدار قدیمی ارسال نمی‌شود.
- Retry خودکار حداکثر ۱۰ بار (قابل تنظیم در Advanced) و فقط با مقدارهای Responseهای قبلی انجام می‌شود و هیچ Request یکسانی دوبار ارسال نمی‌شود.
- Requestهای GET/HEAD/OPTIONS قابل Retry هستند. POST/PUT/PATCH فقط با تنظیم Idempotent یا `Idempotency-Key` Retry می‌شوند و حتی در این حالت فیلدهای Body تغییر نمی‌کنند مگر `allowDataChanges` روشن باشد. DELETE هرگز خودکار Retry نمی‌شود.
- اگر Retry خودکار موفق نشود، اجرا متوقف می‌شود و در Step Panel می‌توان فیلد و مقدار درست را انتخاب کرد، دوباره امتحان کرد و انتخاب را برای اجراهای بعدی ذخیره کرد.
- Tab «Attempts» تاریخچه تلاش‌ها، تغییر هر تلاش، Status و علت توقف را نشان می‌دهد و Request دقیق هر تلاش با Mask شدن مقادیر Sensitive قابل مشاهده است.

Variableها و مقدارهای Response در Scope همان اجرای پیش‌شرط باقی می‌مانند و بین اجراها یا پیش‌شرط‌ها به اشتراک گذاشته نمی‌شوند. مقادیر Sensitive در UI، Logها و تاریخچه Mask می‌شوند.

HTTP Requestها دارای محدودیت‌هایی مانند Timeout، Response Size Limit و محافظت در برابر آدرس‌های خطرناک (SSRF) هستند.

# راه‌اندازی هوش مصنوعی

تحلیل Test Workspace (فهم نیازمندی، معیارهای پذیرش، Test Case، حالات مرزی، ریسک و Automation) با مدل زبانی انجام می‌شود. می‌توان یک یا چند سرویس تعریف کرد.

## گزینهٔ ۱: Ollama محلی (رایگان و خصوصی)

هیچ داده‌ای از سیستم خارج نمی‌شود.

### نصب

اگر سایت ollama.com در دسترس است:

```bash
curl -fsSL https://ollama.com/install.sh | sh
```

اگر ollama.com مسدود است (خطای 403)، همان نسخهٔ رسمی را از GitHub و بدون نیاز به sudo نصب کنید:

```bash
mkdir -p ~/.local/ollama && cd ~/.local/ollama
curl -fL -o ollama.tar.zst https://github.com/ollama/ollama/releases/latest/download/ollama-linux-amd64.tar.zst
tar --zstd -xf ollama.tar.zst && rm ollama.tar.zst
~/.local/ollama/bin/ollama --version
```

### اجرا

```bash
OLLAMA_HOST=127.0.0.1:11434 OLLAMA_KEEP_ALIVE=30m ~/.local/ollama/bin/ollama serve
```

این Terminal باید باز بماند. برای اجرای دائمی می‌توان یک systemd user service برای همین دستور ساخت.

### دانلود مدل

```bash
~/.local/ollama/bin/ollama pull qwen3:8b
```

| مدل | حجم | توضیح |
|---|---|---|
| `qwen3:8b` | ۵٫۲ گیگابایت | تعادل خوب بین کیفیت فارسی و سرعت؛ پیشنهاد پیش‌فرض |
| `qwen3:14b` | ۹٫۳ گیگابایت | کیفیت بهتر، حدود دو برابر کندتر |
| `qwen3:4b` | ۲٫۵ گیگابایت | سریع‌تر، کیفیت پایین‌تر |

مدل را از «تنظیمات ← AI provider» هم می‌توان با دکمهٔ «دانلود مدل» گرفت.

اگر دانلود در انتها با `context deadline exceeded` متوقف شد، همان دستور `pull` را دوباره اجرا کنید؛ دانلود از همان‌جا ادامه پیدا می‌کند.

### ثبت در برنامه

در «تنظیمات ← AI provider» سرویس «Ollama — محلی» را اضافه کنید:

- آدرس: `http://localhost:11434`
- مدل: `qwen3:8b`
- پنجرهٔ متن: `24576`
- Timeout: روی CPU دست‌کم `3600000` (یک ساعت)
- سقف زمان نوشتن هر مرحله: پیش‌فرض `180` ثانیه

سپس «تست اتصال» را بزنید.

### سرعت

روی CPU لپ‌تاپ (بدون GPU) مدل ۸B حدود ۱ تا ۳ توکن در ثانیه تولید می‌کند. خواندن متن تسک نیز چند دقیقه طول می‌کشد.

برای اینکه هیچ مرحله‌ای بیش از حد طول نکشد، «سقف زمان نوشتن هر مرحله» وجود دارد:

- مدل در این سقف متوقف می‌شود و همان پاسخی که تا آن لحظه نوشته استفاده می‌شود؛ مرحله شکست نمی‌خورد.
- مهم‌ترین بخش‌ها (قواعد، APIها، وضعیت‌ها) اول نوشته می‌شوند تا پاسخ کوتاه‌شده هم مفید باشد.
- اگر مرحله‌ای کوتاه شد، هشدار آن در صفحهٔ تحلیل نمایش داده می‌شود.
- عدد کمتر سریع‌تر است و عدد بیشتر نتیجهٔ کامل‌تری می‌دهد. `0` یعنی بدون سقف.

در حین اجرا، تعداد توکن‌هایی که مدل نوشته کنار هر مرحله نمایش داده می‌شود. دکمهٔ «توقف» تحلیل را فوراً متوقف می‌کند.

## گزینهٔ ۲: سرویس رایگان آنلاین

تحلیل را به چند دقیقه کاهش می‌دهد. در «تنظیمات ← AI provider» یکی از Presetها را انتخاب کنید و کلید API رایگان آن را وارد کنید:

| سرویس | دسترسی از ایران | محل ساخت کلید |
|---|---|---|
| Pollinations | بدون VPN | کلید لازم نیست |
| Hugging Face Inference | بدون VPN | huggingface.co/settings/tokens |
| GitHub Models | بدون VPN | توکن fine-grained با مجوز models |
| SambaNova Cloud | بدون VPN | cloud.sambanova.ai |
| Cerebras | ممکن است VPN لازم باشد | cloud.cerebras.ai |
| Mistral | بدون VPN | console.mistral.ai |
| Groq، Google Gemini، OpenRouter | ممکن است VPN لازم باشد | سایت هر سرویس |

نکات این سرویس‌ها:

- متن تسک و PRD برای سرویس ارسال می‌شود. تا وقتی گزینهٔ «اجازه می‌دهم متن نیازمندی به این سرویس ارسال شود» را تیک نزنید، هیچ داده‌ای ارسال نمی‌شود.
- اطلاعات محرمانهٔ داخل متن (توکن، رمز) پیش از ارسال پوشانده می‌شود.
- کلید API رمزنگاری‌شده ذخیره می‌شود و دوباره نمایش داده نمی‌شود.

Pollinations بدون حساب و کلید کار می‌کند. نسخهٔ رایگان آن حداکثر ۳ درخواست هم‌زمان می‌پذیرد و طول هر پاسخ را محدود می‌کند؛ برنامه این محدودیت‌ها را رعایت می‌کند و موارد کامل هر پاسخ را نگه می‌دارد. برای نتیجهٔ کامل‌تر، یک سرویس با کلید رایگان (مثل GitHub Models) هم اضافه کنید.

## حداکثر زمان تحلیل

در «تنظیمات ← AI provider»، «حداکثر زمان یک تحلیل» به‌طور پیش‌فرض ۱۸۰ ثانیه است:

- هر مرحله سهم مشخصی از این زمان دارد تا هیچ مرحله‌ای وقت بقیه را نگیرد.
- در پایان زمان، مراحلی که تمام شده‌اند ذخیره می‌شوند و بقیه با پیام «تحلیل به سقف زمانش رسید» رد می‌شوند.
- Test Caseها پیش از بقیهٔ مراحل موازی شروع می‌شوند.
- `0` یعنی بدون سقف.

با Pollinations، تحلیل کامل TEST 2 در حدود ۲٫۵ دقیقه تمام شد. مدل محلی روی CPU در این زمان فقط نتیجهٔ کوتاهی می‌دهد.

## استفاده هم‌زمان از چند سرویس

با بیش از یک سرویس، در بخش «هر سرویس چه کاری انجام دهد» می‌توان برای هر مرحله سرویس جدا انتخاب کرد: تحلیل، Test Case، حالات مرزی، بازبینی، Automation، ترجمه و یادگیری.

- در حالت «خودکار» اولین سرویس سالم به ترتیب استفاده می‌شود.
- اگر سرویسی در دسترس نباشد یا محدودیت نرخ بدهد، سرویس بعدی امتحان می‌شود.
- مرحلهٔ بازبینی تا جای ممکن با مدلی غیر از مدل نویسندهٔ Test Caseها انجام می‌شود.
- مراحل مستقل روی سرویس‌های مختلف هم‌زمان اجرا می‌شوند. روی یک سرویس، درخواست‌ها پشت سر هم اجرا می‌شوند.

## یادگیری از اصلاحات

هر اصلاح در Test Workspace ثبت می‌شود و پس از چند اصلاح به «رهنمود» تبدیل می‌شود. این رهنمودها در «تنظیمات ← آنچه تحلیل یاد گرفته» قابل مشاهده، ویرایش، خاموش کردن و حذف هستند و قواعد دلخواه هم می‌توان اضافه کرد. برای ساختن رهنمود از اصلاحات، یک سرویس برای مرحلهٔ «یادگیری» لازم است.

## رفع مشکل

| مشکل | علت و راه‌حل |
|---|---|
| `fetch failed` یا «هیچ سرویس هوش مصنوعی‌ای نتوانست این مرحله را انجام دهد» | Ollama اجرا نیست یا آدرس اشتباه است. `curl http://localhost:11434/api/version` را امتحان کنید. |
| `model '...' not found` | مدل دانلود نشده؛ `ollama pull <model>` را اجرا کنید یا از Settings دانلود کنید. |
| «The model did not answer in time» | Timeout سرویس برای CPU کم است؛ آن را به `3600000` یا بیشتر برسانید. |
| «مدل به سقف زمان نوشتن رسید» | مرحله کوتاه شده است؛ برای نتیجهٔ کامل‌تر سقف زمان نوشتن را بیشتر کنید. |
| تحلیل در میانه ناپدید شد | API دوباره راه‌اندازی شده است (مثلاً با تغییر کد در حالت `dev:api`). تحلیل‌ها در حافظهٔ API اجرا می‌شوند؛ تحلیل را دوباره اجرا کنید. پیشوند مشترک Prompt در Ollama Cache می‌شود و اجرای دوباره سریع‌تر شروع می‌شود. |
| سرویس آنلاین با خطای 403 | سرویس از منطقهٔ شما مسدود است؛ از سرویس‌های «بدون VPN» جدول بالا استفاده کنید. |

# اجرا بدون Docker

ابتدا وارد Root اصلی پروژه شوید.

باید در مسیری باشید که فایل `package.json` در کنار پوشه‌های `apps` و `packages` قرار دارد.

اگر پروژه از فایل ZIP استخراج شده است، ممکن است یک Directory اضافه ایجاد شده باشد و لازم باشد یک Level داخل‌تر بروید.

## 1. نصب Dependencyها

```bash
npm install
```

## 2. Generate کردن Prisma Client

Prisma Schema این پروژه در مسیر زیر قرار دارد:

```text
apps/api/prisma/schema.prisma
```

Prisma Client را Generate کنید:

```bash
npx prisma generate --schema=apps/api/prisma/schema.prisma
```

در صورت موفقیت باید پیام مربوط به Generated شدن Prisma Client نمایش داده شود.

## 3. بررسی Build

```bash
npm run build
```

این مرحله خطاهای TypeScript، Prisma و سایر مشکلات Build را قبل از اجرای محیط مشخص می‌کند.

اگر Build بدون خطا انجام شد، مراحل بعدی را ادامه دهید.

## 4. اجرای Database

در Terminal اول و از Root پروژه اجرا کنید:

```bash
npm run demo:db
```

این دستور PostgreSQL داخلی پروژه را روی Port `5433` اجرا می‌کند، Tableهای موردنیاز را می‌سازد و فایل `.env` را آماده می‌کند.

این Terminal باید هنگام استفاده از QA Workbench باز بماند.

## 5. اجرای API

در Terminal دوم:

```bash
npm run dev:api
```

API به‌صورت پیش‌فرض روی Port `3001` اجرا می‌شود.

Health Check:

```text
http://localhost:3001/api/health
```

## 6. اجرای Web

در Terminal سوم:

```bash
npm run dev:web
```

رابط کاربری:

```text
http://localhost:3000
```

## 7. ایجاد Demo Data

بعد از بالا آمدن API:

```bash
npm run demo:seed
```

بعد از این مرحله می‌توانید Demo Flow سیستم را بدون Jira یا Redis اجرا کنید. اگر سرویس هوش مصنوعی تنظیم شده باشد، تحلیل Demo Issue هم در پس‌زمینه شروع می‌شود.

# اگر Build قبل از Database اجرا نشد

اگر `npm run build` به Environment Variable یا Database نیاز داشت، ابتدا Database را اجرا کنید.

### Terminal 1

```bash
npm install
npm run demo:db
```

این Terminal را باز نگه دارید.

سپس در Terminal دیگری:

```bash
npx prisma generate --schema=apps/api/prisma/schema.prisma
npm run build
```

بعد:

```bash
npm run dev:api
```

و در Terminal دیگری:

```bash
npm run dev:web
```

بعد از بالا آمدن API:

```bash
npm run demo:seed
```

# اجرا با Docker

Environment را آماده کنید:

```bash
cp .env.example .env
cp .env apps/api/.env
```

Dependencyها را نصب کنید:

```bash
npm install
```

سرویس‌های Docker را اجرا کنید:

```bash
npm run docker:up
```

Prisma Client را Generate کنید:

```bash
npx prisma generate --schema=apps/api/prisma/schema.prisma
```

Migrationها را اجرا کنید:

```bash
npm run db:migrate
```

API را اجرا کنید:

```bash
npm run dev:api
```

و در Terminal دیگری:

```bash
npm run dev:web
```

در حالت Docker:

- PostgreSQL: Port `5432`
- Redis: Port `6379`
- Web: Port `3000`
- API: Port `3001`

# رفع خطای Prisma Schema

اگر دستور:

```bash
npx prisma generate
```

با خطای:

```text
Could not find Prisma Schema that is required for this command
```

مواجه شد، علت این است که Prisma Schema پروژه در مسیر Default قرار ندارد.

Schema اصلی پروژه:

```text
apps/api/prisma/schema.prisma
```

بنابراین دستور صحیح این است:

```bash
npx prisma generate --schema=apps/api/prisma/schema.prisma
```

از Schema موجود در مسیر زیر برای Generate کردن Client استفاده نکنید:

```text
node_modules/.prisma/client/schema.prisma
```

# رفع خطاهای Build و Prisma Type

اگر هنگام اجرای:

```bash
npm run build
```

خطاهای TypeScript مانند `TS7006` در بخش‌هایی که اطلاعات Jira را از Prisma دریافت می‌کنند مشاهده شد، ابتدا Prisma Client را دوباره Generate کنید:

```bash
npx prisma generate --schema=apps/api/prisma/schema.prisma
```

سپس:

```bash
npm run build
```

تابع‌هایی مانند `loadIssue()` ممکن است به Typeهای Generated توسط Prisma وابسته باشند.

برای رفع سریع TypeScript Error نباید پارامترهای این بخش‌ها بدون بررسی با `any` Type شوند.

اگر بعد از Generate کردن Prisma Client همچنان خطای Type مربوط به `loadIssue()` باقی ماند، Return Type تابع باید به‌صورت Explicit با Typeهای Generated خود Prisma تعریف شود.

بسته به Query موجود می‌توان از Typeهایی مانند:

```typescript
Prisma.JiraIssueGetPayload
```

استفاده کرد تا Type خروجی مستقیماً با Prisma Schema و Query واقعی هماهنگ باشد.

# تست‌ها

```bash
npm run test        # Testهای API (Jest)، شامل تحلیل هوش مصنوعی، پیش‌شرط‌ها، مراحل UI و i18n parity
npm run typecheck
npm run lint
npx tsx --test apps/web/lib/curl/parse-curl.spec.ts packages/shared/src/secrets.spec.ts
```

Testهای پیش‌شرط‌ها و تحلیل هوش مصنوعی از Mock API و مدل شبیه‌سازی‌شده استفاده می‌کنند و به سرویس یا مدل واقعی Request ارسال نمی‌کنند.

Testهای مرحلهٔ UI با Chrome واقعی و یک وب‌سایت آزمایشی محلی اجرا می‌شوند (ضبط، اجرای پس‌زمینه، پیدا کردن عنصر بعد از تغییر صفحه، رمزنگاری رمز عبور و اتصال Token به درخواست بعدی). اگر Chrome، Chromium یا Edge نصب نباشد، این Testها رد (Skip) می‌شوند.

# مشکلات Port

اگر Port `3001` اشغال باشد، ابتدا Process مربوط به آن را پیدا کنید:

```bash
lsof -i :3001
```

بعد از متوقف کردن Process قبلی، API را مجدداً اجرا کنید:

```bash
npm run dev:api
```

اگر Port `5433` اشغال باشد:

```bash
lsof -i :5433
```

بعد از متوقف کردن Instance قبلی:

```bash
npm run demo:db
```

# مسیر Demo

برای مشاهده Flow کامل سیستم بدون نیاز به سرویس‌های خارجی:

1. با `npm run demo:seed` Demo Issue را بسازید، یا در صفحه Jira یک Issue را از Excel/CSV یا به‌صورت دستی وارد کنید.
2. وارد صفحه Jira شوید.
3. Issue را باز کرده و وارد Workspace شوید.
4. در صورت وجود، PRD را اضافه کنید و «تحلیل فارسی» یا «تحلیل انگلیسی» را بزنید.
5. معیارهای پیشنهادی را تأیید، اصلاح یا رد کنید.
6. نتیجه را در زبانه‌های Requirement Analysis، Strategy، Test Cases، Edge Cases و Risks ببینید و هر جا لازم است اصلاح کنید.
7. اصلاحات خود را در «تنظیمات ← آنچه تحلیل یاد گرفته» ببینید.
8. Test Case موردنظر را اجرا کنید.
9. در صورت Failure از Execution یک Bug ایجاد کنید.
10. یک Test Suite ایجاد کنید.
11. وارد بخش «پیش‌شرط‌ها» شوید و یک پیش‌شرط جدید بسازید.
12. با «افزودن ← مرحلهٔ UI (مرورگر)» ورود به یک وب‌سایت را ضبط کنید، ذخیره کنید و اجرا کنید.
13. با «Import cURL» چند دستور cURL را Paste کنید، Review را بررسی و ارتباط‌های پیشنهادی را تأیید کنید.
14. پیش‌شرط را اجرا کرده و نتیجه Stepها را در Request Flow و Step Panel مشاهده کنید.
15. برای Step ناموفق، کارت خطای پاسخ را ببینید؛ از Tab «Data Mapping» یا Response Explorer مقدار درست را از پاسخ یک Step قبلی انتخاب کرده و «اجرا تا همین مرحله» را بزنید.
16. Mappingها را پاک کنید و «تشخیص خودکار Mappingها» را بزنید؛ سپس پیش‌شرط را دوباره اجرا کنید.

برای اجرای این Demo Flow نیازی به Jira یا Redis نیست؛ مراحل تحلیل به یک سرویس هوش مصنوعی (مثلاً Pollinations یا Ollama محلی) نیاز دارند.
